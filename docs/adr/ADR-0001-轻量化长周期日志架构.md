# ADR-0001 轻量化长周期日志架构

- 状态：**接受（架构方向）；首批实现中，真实环境与性能未验收**。
- 提议日期：2026-11-09。
- 接受与实施授权：2026-11-10，用户明确采用 ClickHouse，批准生成初始化 SQL 与本机隔离 SQLite 测试。
- 相关：[产品规划](../spec/产品规划.md)、[一期实施方案](../spec/一期实施方案.md)、[首批存储实施合同](../spec/首批存储实施合同.md)。

## 背景

约 1000 台设备、后台自定义通常 1～3 年保留、尽可能轻量。最初的全 SQLite 与 Api/Ingest 双宿主是初始化草案。长期日志规模取决于平均 EPS 与报文长度，可能达到数十亿至数千亿条，不能凭设备数量或服务数判断性能。

## 已接受决定

1. 单机一个 .NET 模块化宿主加一个非复制 ClickHouse 服务；SQLite 内嵌保存控制数据与可靠审计，不引入必选 MQ、缓存、独立搜索集群或对象服务。
2. Syslog.Api 引用 Syslog.Ingest 模块，Ingest 不反向依赖 Api。管理服务拥有 SQLite 写入权，日志存储服务拥有 ClickHouse 写入权；Engine 保持无 I/O。
3. 接收、暂存、写入与查询各有预算；写入结果未知先保留并停发，不假定有限数据库去重窗口提供端到端 exactly-once。
4. 保留期内原文与结构化详情在线可查是产品目标；当前仅实现最长 30 天的单请求检索，历史任务尚未实现。冷热本地卷可选，离线归档非默认。
5. 普通启动不建库或迁移；显式初始化 SQL 与维护命令可审阅。保留设置由后台管理，历史变更/物理清理由后续授权任务协调；当前无自动删除 TTL，也未实现物理清理任务。

后续授权补充：ClickHouse 日志存储首次访问时自动创建配置所需的缺失库表，并检查表结构。SQLite 初始化与既有库表迁移仍沿用显式流程。管理员确认后可清空 ClickHouse 日志表，意图和结果写入 SQLite 审计。历史保留期限调整和定时物理清理仍待实现。
6. 厂商接入、中文全文索引、稳定查询时延、恢复对账与长期容量必须单独验证，不由架构采纳推导为能力已达标。

## 理由与替代方案

ClickHouse 承担日志分析，SQLite 提供控制事务，使必需服务维持两个。纯 SQLite 或压缩文件加索引可以降低外部依赖，但完整检索、索引重建、保留与恢复将增加自建存储成本；若未来工作负载证明另有优势，可用新 ADR 替代。本决定没有宣称 ClickHouse 任意查询秒回，也不把预算压缩率当实测。

## 影响与本轮范围

本决定替代早期“全库 SQLite、Ingest 唯一写者、Api 只读、双宿主不引用”的草案。工程规则、目录和模块说明已同步。已有基础解析、接收/暂存模块、ClickHouse HTTP 写入/检索、SQLite 管理员/会话/来源/审计和 API；监听默认关闭。

Web 管理台、细分权限、告警、回放、导出、历史保留变更、清理、备份恢复尚未完成。当前仅管理员角色；关键词限区分大小写的 ASCII 全词 AND，中文和纯符号明确返回不支持。

## 验证与风险

本轮授权可用于生成 SQL 和本机隔离 SQLite 测试，不包含真实 ClickHouse 建库、Syslog 监听、设备配置、生产部署或发布。首批 HTTP/流/暂存测试采用替身；具体构建测试记录以本地运行为准。

单宿主共享故障域，单节点无自动高可用；跨 SQLite、文件与 ClickHouse 无统一事务。sending 批次需要人工对账，acked 回收残留使启动明确失败，恢复工具尚未完成；文件目录项掉电持久性、确认残留回收与真实磁盘故障仍需验证。后续按代表性流量与目标硬件验证，再确定容量和性能档位。
