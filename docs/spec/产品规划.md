# 通研 Syslog 产品规划

编制：2026-11-09；状态更新：2026-11-10。本文保留完整一期规划与后续路线图；用户已采纳单宿主和 ClickHouse 架构，首批后端代码已建立。实际交付边界见[首批存储实施合同](首批存储实施合同.md)，不代表全部功能或性能目标已经完成。

通研 Syslog 为交换机、ESXi 和其他系统提供统一的日志接收地址，集中保存原始报文与解析结果，让使用者从一个网页完成查询、故障分析、告警和留存管理。本次已确认的约束是：**约 1000 台设备、保留期由用户在后台自定义、通常保留 1～3 年、系统尽可能轻量级**。

已采纳 **一个 .NET 应用服务 + 一个单节点 ClickHouse 服务**；管理数据和审计使用内嵌 SQLite，替代早期全 SQLite/双宿主草案，见[已接受 ADR](../adr/ADR-0001-轻量化长周期日志架构.md)。完整保留期在线查询仍是产品目标；首批仅有最长 30 天单请求检索，历史任务、Web 管理台、告警、回放、导出与物理清理未实现。监听默认关闭，真实设备、ClickHouse 与性能尚未验收。

## 需求理解

| 使用需要 | 产品行为 | 边界 |
| --- | --- | --- |
| 给设备填写一个 Syslog 地址 | 提供按协议、端口、设备型号整理的接入向导，能验证首条日志 | 不自动登录交换机或 ESXi 修改配置 |
| 集中管理约 1000 台设备 | 批量登记、分组、标签、接收状态和未登记来源发现 | 设备数量不能代替日志速率与容量测量 |
| 快速查问题 | 按时间、设备组、主机、严重级别、关键字和接口等字段检索 | 历史全量扫描不承诺与近期精确查询一样快 |
| 分析多设备的故障过程 | 时间线、上下文、趋势、Top 来源、同窗口关联和保存查询 | 日志中的相关性不自动等于故障因果关系 |
| 长期保存 | 后台配置全局与设备组保留策略，常用 1、2、3 年并支持自定义 | 缩短历史保留须预览影响并确认；延长不能恢复已物理删除数据 |
| 轻量部署维护 | 单机、两个常驻服务、无必选消息队列或独立搜索服务 | 数据量本身仍需要磁盘，单机不具备自动高可用 |

“各个系统的日志”指系统实际转发的内容。ESXi 宿主日志、虚拟机内部操作系统/应用日志、vCenter 日志分别登记与接入。交换机原生 Syslog 可以直连；Windows、容器和未实现 Syslog 的应用需另配受控转发器，不能仅填写地址就自动采集任意文件。

## 用户与使用闭环

主要用户是基础设施运维人员，兼顾安全排障人员和只读审计人员。角色建议为管理员、运维、只读查询、审计员，并按设备组限制访问；原文、导出、删除和用户管理分别授权。

1. 管理员设置内网接收地址、协议、监听器、证书及容量预算。
2. 批量登记设备，填写品牌型号、固件版本、发送来源、所属组、时区和保留策略。
3. 按设备向导配置发送，核对“已收到、已解析、已入库”的合成测试标记。
4. 运维人员通过时间范围和设备组定位故障，展开原文与相关日志。
5. 将常用排障条件保存为查询，将明确异常配置为告警规则。
6. 管理员查看增长趋势、到期清理与备份恢复情况，按容量预测调整策略。

## 首批场景

| 场景 | 检索和分析方式 | 依赖 |
| --- | --- | --- |
| 交换机端口反复上下线 | 设备 + 接口 + link 事件，查看 5 分钟内变化次数和上下文 | 对应型号确实发送该事件且字段适配完成 |
| 交换机重启、配置变更、登录失败 | 主机时间线、事件类别、操作者字段及原文 | 日志包含的身份不作为平台登录身份 |
| ESXi 存储或网络异常 | 主机 + 组件 + 关键字，关联同时间窗口内其他设备日志 | 以实际转发报文为依据，不宣称覆盖全部虚拟化事件 |
| 多设备同时发生故障 | 按设备组、时间和事件类别聚合，再逐条核对 | 时钟同步与时间质量标记 |
| 查一年前某台设备发生了什么 | 指定设备和日期，在统一检索页查询完整保留数据 | 历史查询可转后台任务并显示进度 |
| 排查为什么收不到日志 | 检查监听状态、最后接收/入库、来源匹配、证书、队列和丢弃 | 静默只代表没有新报文，不直接判断设备离线 |

## 功能优先级

P0 是可试用核心，P1 是一期交付必须补齐的管理能力，P2 是独立评估的后续增强。P0 完成不代表一期全部完成。详细行为与验收见[功能需求清单](功能需求清单.md)。

| 模块 | P0 | P1 | P2 |
| --- | --- | --- | --- |
| 接收与设备 | UDP/TCP/TLS、1000 设备台账、批量导入、接入验证、来源限速 | 按实际品牌版本扩充向导与诊断 | 多站点中继、接收高可用 |
| 解析 | RFC 5424/3164、通用交换机与 ESXi 基础解析、失败留原文 | 自定义声明式解析、观察/生效/回滚、幂等回放 | 更多行业格式 |
| 查询 | 设备/时间/级别/关键字、上下文、原文、稳定翻页 | 保存查询、受控导出、历史查询任务、结构化组合条件 | 更复杂的分析语言 |
| 分析与告警 | 数量趋势、级别分布、接收健康、关键字与频率规则 | 有界关联窗口、静默/冷却、Webhook 重试与失败状态 | 邮件等额外通知渠道 |
| 留存与运维 | 自定义保留、容量估算、磁盘阈值、可靠审计 | 历史策略调整、备份恢复、删除核验与完整运行观测 | 对象存储归档和回读 |
| 权限 | 登录、会话、设备组权限、只读角色、HTTPS | 导出/原文细分授权、审计检索与受控导出 | 外部身份提供商 |
| 跨产品日志 | 通用 Syslog 接入合同 | 同系列产品的事件适配；外部 IP 归属查询按需异步且默认关闭 | 更多跨产品查询视图 |

一期明确排除：主动封禁或阻断、完整 SIEM、内置 AI 分析、SaaS 多租户、桌面客户端、跨集群与分布式存储。2026-11-11 用户已确认 MCP 接入扩展，其页面、39 个工具、权限和完整审计源码已实现，见 [MCP 服务需求与设计](MCP服务需求与设计.md)；本轮仅在隔离环境验证，不部署。品牌沿用通研技术，不改变对外发布状态。

## 管理台页面

| 页面 | 核心内容 |
| --- | --- |
| 总览 | 今日接收/入库、当前 EPS、活跃与静默来源、失败与丢弃、磁盘剩余、可保留天数、最近告警 |
| 日志检索 | 顶部时间与设备组筛选，中部趋势和结果列表，侧栏详情；默认最近 15 分钟 |
| 日志详情 | 原文、字段、来源身份、两种时间、解析器版本、失败/截断标记、前后文 |
| 设备与接入 | 搜索、分组、批量导入、品牌/型号/固件、协议地址、合成测试向导、最近接收与入库 |
| 解析器 | 样例测试、覆盖字段、版本差异、观察结果、启用与回滚、历史回放任务 |
| 告警中心 | 待确认、已确认、静默、恢复、通知失败；每项链接到对应日志 |
| 分析 | 时间趋势、级别分布、Top 来源、常用排障视图、保存查询 |
| 存储与留存 | 全局/组策略、1/2/3 年及自定义、容量预测、历史变更预览、到期清理状态 |
| 系统与审计 | 账号角色、接收监听、证书状态、配置版本、备份任务、操作审计 |

日志按纯文本展示，支持桌面主要视口和错误/空态。用户看见的是日志业务状态；SQL、存储引擎参数等留在运维详情，不要求普通查询人员理解数据库实现。

## 轻量化与容量取舍

轻量化优先减少服务数量、内存常驻量、维护工作和不必要索引。默认不依赖 Kafka、Redis、Elasticsearch/OpenSearch、Kubernetes、Grafana 或对象存储服务。React 前端构建为静态文件，由 .NET 同源托管。

1000 台设备若每台平均 1 条/秒，则总量为 1000 EPS，一年约 **315.36 亿条**。以每条原文 1 KiB、原文加结构字段和索引压缩后合计为原文 0.4 倍估算，三年约 **38.75 TB** 数据；预留 30% 空闲后的可用数据卷约 **55.36 TB**，尚不含备份。该系数只是预算假设，不是压缩效果承诺。

因此，先采样再采购：测总平均/峰值 EPS、报文长度、压缩后每条字节数和常用查询，再确定磁盘与 CPU。完整公式、低/中/高场景、资源预算和降本方案见[一期实施方案](一期实施方案.md)。

如存储预算不足，按顺序考虑：减少无价值 Debug 来源、逐组设置合理保留、历史数据使用较低成本磁盘、限制全历史查询并发、最后再评估归档。筛选和缩短保留都由用户决定，系统不自动丢弃历史原文或只保留统计值。

## 分期与工作量估算

按 1 名熟悉 .NET/React 的全栈开发者、可获得设备测试支持估算，**一期约 10～15 人周**，不含硬件采购、跨厂商适配等待及需求变更；这是排期预算，不是交付承诺。

| 阶段 | 估算 | 交付物与退出条件 |
| --- | --- | --- |
| M0 方案与容量验证 | 1～2 周 | 确认 ADR、设备矩阵、ID 方案；在获准环境测代表性流量和存储收益 |
| M1 接收与可恢复入库 | 2～3 周 | 工程初始化、三类传输、原文与解析、持久缓冲、断点恢复、分阶段指标 |
| M2 检索与首批试用 | 2～3 周 | 设备台账、账号权限、查询/详情、两类设备实测；试用版本不宣称一期完工 |
| M3 长期留存与运维 | 2～3 周 | 自定义保留、历史变更、容量、备份恢复、导出与审计 |
| M4 告警与一期验收 | 3～4 周 | 规则版本、自定义解析、告警、家族适配、1000 来源压测、安全与浏览器验收 |

试点建议从 10～20 台具有代表性的设备开始，逐步增加到 100、300、1000 台。最终设备接入、监听端口、服务器和部署动作另行按环境授权。

## 待确认事项

方案已采用用户明确的规模、留存和轻量化要求。实施前还需确认：交换机品牌/型号/固件和 ESXi 版本分布；代表性平均/峰值 EPS；可用服务器与磁盘预算；历史查询期望时延；可接受停机与数据恢复目标；是否保留全部级别和原文；后台账号数及设备组隔离规则。

这些信息用于定型与验收，不影响本方案作为完整评审草案使用。后续开发遵循已接受架构；新增范围与实际环境动作分别确认。
